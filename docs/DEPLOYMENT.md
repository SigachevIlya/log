# Публикация LOG. 0.5.2 на GitHub Pages

Это инструкция для будущей публикации. Репозиторий и хостинг автоматически не создавались, workflow не запускался, сайт не опубликован.

## Первая пробная публикация 0.5.2

Публикация для проверки на физическом iPhone явно поручена пользователем после локальных проверок. Репозиторий: https://github.com/SigachevIlya/log. Целевой адрес: https://sigachevilya.github.io/log/. Для него `LOG_BASE_PATH=/log/`; существующий workflow вычисляет этот путь из имени репозитория. В Settings → Pages должен быть выбран источник GitHub Actions. Запуск — вручную, workflow `Check and optionally publish LOG.`, ветка `main`, `publish=true`, `base_path=/log/`.

Публикуются только исходники и статическая сборка workflow. Локальные `artifacts/`, результаты тестов/трассы, сгенерированные визуальные материалы, зависимости, временные сборки и резервные копии исключены через .gitignore. Начальные A/B/C и данные в тестах являются штатной программой и синтетическими сценариями; пользовательская IndexedDB в репозиторий не входит. Фактический статус публикации проверяется в Actions и по HTTPS, а физический Safari остаётся следующим этапом. Версия 1.0 не присваивается.

Тестовый portable build и его preview используют одинаковый `LOG_BASE_PATH='./'`; затем отдельный финальный build использует `/log/`. Не передавайте финальный base в preview переносимой тестовой сборки: корневые URL тестов будут перенаправляться, вызывая лишние загрузки страниц. Исправление не меняет base опубликованного приложения и не ослабляет браузерные проверки.

## Подготовка

1. До смены адреса откройте старый дневник → Настройки → Данные и резервные копии. Создайте JSON, скачайте его или передайте через «Поделиться» и убедитесь, что файл действительно появился в выбранном месте. CSV для переноса не подходит.
2. Создайте собственный GitHub-репозиторий и загрузите исходный проект с package-lock.json и `.github/workflows/pages.yml`. Не добавляйте node_modules, личные JSON/CSV или содержимое браузерных хранилищ. В проекте нет серверных секретов или базы пользователя.
3. В Settings → Pages → Build and deployment выберите Source: GitHub Actions. В Environment `github-pages` можно настроить разрешённую ветку и дополнительное ручное подтверждение развёртывания.
4. Откройте Actions → Check and optionally publish LOG. → Run workflow. Сначала оставьте `publish` выключенным: выполнятся проверки и подготовка артефакта без публикации. Поле `base_path` можно оставить пустым.
5. После успешной проверки запустите workflow с `publish` включённым. Публикуется только проверенный `dist`; на обычный push автоматического развёртывания нет.

Workflow использует Node 24, `npm ci`, unit-тесты, TypeScript, production-сборку, браузерные сценарии и отдельные PWA-тесты. LAN-сценарии в CI пропускаются без адреса локальной сети. Финальный Pages-артефакт собирается после проверок с выбранным base. Права публикации есть только у deploy job; build имеет `contents: read`. Схема workflow и environment соответствуют [документации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Адрес и base

Для репозитория `owner/LogApp` по умолчанию выбран `/LogApp/`, ожидаемый адрес — `https://owner.github.io/LogApp/`. Для `owner/owner.github.io` выбран `/`. При собственном домене укажите `/` и отдельно настройте домен/DNS/HTTPS в GitHub Pages. Проект не подставляет чужой домен и не создаёт CNAME.

Локальная проверка абсолютного base в PowerShell:

```powershell
$env:LOG_BASE_PATH = '/LogApp/'
npm.cmd run build
npm.cmd run preview
# Откройте http://localhost:4173/LogApp/#/settings/application
Remove-Item Env:LOG_BASE_PATH
```

По умолчанию `base='./'`: сборка переносима между корнем и подкаталогом с завершающим `/`. Разрешены только относительный `./` или локальный абсолютный путь из сегментов с буквами ASCII, цифрами, `_`, `-`, `.`; сегменты `.`/`..`, query, fragment, обратные слеши и внешние URL запрещены.

Hash-маршруты, manifest, иконки, lazy chunks и регистрация service worker используют путь приложения. `start_url` и manifest scope относительные `./`, scope worker ограничен каталогом. Сборка создаёт `.nojekyll`. Настройка серверного SPA fallback для вложенных hash-адресов не требуется.

## Первый запуск и перенос дневника

1. Дождитесь завершения deploy и откройте выданный HTTPS-адрес в Safari.
2. Откройте Настройки → Приложение. Дождитесь «Готово к автономной работе». При ошибке подготовки останьтесь в сети и повторите попытку; первый запуск без сети невозможен.
3. В Данных восстановите заранее сохранённый JSON. Проверьте дату, сводку и предупреждение о полной замене. При необходимости сначала создайте копию данных нового адреса.
4. Проверьте программу, историю, следующую тренировку и активную сессию. Импортированные черновики открываются отдельно и применяются только явным сохранением.
5. Установите через Safari → Поделиться → На экран «Домой». Запустите иконку, проверьте данные и статус готовности, затем включите авиарежим и повторно откройте приложение. Если отдельный запуск не видит прежний дневник, восстановите JSON внутри установленного приложения.

`localhost`, локальный IP, HTTP/HTTPS, домены, порты, другие браузеры и профили — разные origin/хранилища. Перенос выполняется JSON-файлом, синхронизации нет. Каталоги одного origin не изолируют IndexedDB: на одном домене не следует размещать несколько независимых дневников LOG. с одним именем базы. Старое хранилище не удаляйте, пока не проверили перенос и файл резервной копии.

## Следующее обновление

Сформируйте актуальную резервную копию, измените исходники/версию и выполните workflow. В приложении новая сборка сначала полностью загружается в отдельный кэш. Уведомление предлагает «Обновить» или «Позже»; само появление сборки не перезагружает страницу. Завершите/отмените активную тренировку, сохраните или закройте изменённые редакторы во всех вкладках. Затем нажмите «Обновить».

Вкладка с неизвестным состоянием тоже откладывает обновление: закройте её или откройте заново. Другие вкладки не перезагружаются принудительно; после активации им предлагается загрузить новую версию. Старый кэш сохраняется, пока открытые старые вкладки могут обращаться к нему. Обновление shell и удаление кэшей не очищают IndexedDB и черновики.

## Что проверить после реальной публикации

- HTTPS, правильный `/имя-репозитория/`, открытие вложенных hash-ссылок и отсутствие 404 у иконок/chunks/manifest/sw.js.
- Готовность офлайн, реальное закрытие/повторный запуск с иконки без сети и сохранение результатов.
- На физическом iPhone 8 / iOS 16: установка, safe-area, клавиатура, скачивание/«Сохранить в Файлы»/«Поделиться», выбор JSON, восстановление и обновление между двумя опубликованными версиями.
- Наличие отдельного файла копии вне браузера. Удаление сайта/приложения, очистка хранилища, приватный режим и ограничения ОС могут удалить локальный дневник. PWA-кэш не является резервной копией.

Локальные эмуляции этих сценариев описаны в README. Реальное размещение, TLS/CDN GitHub Pages, iOS и системные панели передачи файлов в текущей среде не проверялись.
